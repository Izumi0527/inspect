# 设备管理页面 UI 恢复与旧代码清理设计

日期：2026-03-10

## 背景

当前设备管理页已经完成了列表、统计、详情、编辑、批量更新、批量删除、批量探测等前后端联调，但页面 UI 出现了“新旧代码混搭”的问题：

- 主页面仍然沿用旧骨架结构，导致布局、按钮层级、留白和组件容器与当前站点设计体系不一致。
- 批量操作链路同时存在 `BulkDeviceUpdate` 与 `BulkOperationModal` 两套历史组件，职责重叠且调用方式跨代。
- `BulkDeviceUpdate` 仍然使用旧式 `Modal + 直接容器` 结构，没有对齐当前原子组件里的 `ModalContent` / `SimpleModal` 语义。
- 最终结果是：业务链路虽然能工作，但页面展示退回到了旧版实现，与用户当前期望的设备管理页样式不一致。

## 目标

将设备管理页恢复到“截图 1”对应的新页面形态，同时清理旧骨架代码，保留已完成的前后端对接能力。

成功标准：

- 设备管理页继续使用真实后端 API，不回退到假数据或静态占位。
- 页面主视图恢复为“统计卡片 + 设备列表卡片 + 头部操作区 + 规范弹层”的新布局。
- 旧批量交互残留代码被识别并清理，不再出现双轨实现。
- 批量更新重新回到规范弹层中展示，不再出现页面内嵌旧骨架或错误铺展。
- 现有的跨页选择、筛选重置、详情弹窗性能/健康检查、批量更新等业务能力保持不变。

## 问题归因

### 1. 设备管理页容器结构被旧版骨架覆盖

`DeviceManagementView.tsx` 当前聚合了多个阶段的实现，除了真实数据链路外，也把旧版容器和批量操作呈现方式一起保留下来了。这导致页面虽然能跑，但视觉结果停留在旧版。

### 2. 批量更新存在跨代组件混用

代码里同时存在：

- `BulkDeviceUpdate.tsx`
- `BulkOperationModal.tsx`

其中 `DeviceManagementView.tsx` 直接引用 `BulkDeviceUpdate.tsx`，而 `BulkOperationModal.tsx` 内部又再次引用 `BulkDeviceUpdate.tsx`。这说明批量操作流程曾经过一次重构，但旧入口没有被删除。

### 3. 弹层实现未完全迁移到当前设计系统

当前项目的模态体系已经基于 `ModalContent` / `SimpleModal` 收敛，但设备管理页部分批量交互仍采用旧式写法，容易在新布局和新样式体系中出现异常展示。

## 方案比较

### 方案 A：只修补 `BulkDeviceUpdate` 弹层写法

优点：

- 改动最小，风险低。

缺点：

- 无法彻底清理设备页里的旧实现残留。
- 后续仍可能因为双轨组件并存再次回退。

### 方案 B：识别并移除旧骨架代码，恢复设备页为单一新实现

优点：

- 能从根本上解决“新旧代码混搭”问题。
- 页面结构、批量操作入口和弹层实现都能回到当前设计体系。
- 保留已打通的数据与业务链路，避免重复做联调。

缺点：

- 需要同步调整测试，以便保护“恢复后的页面结构”。

### 方案 C：设备页彻底重构

优点：

- 理论上最彻底。

缺点：

- 改动过大，容易破坏现有前后端闭环，不适合本轮修复。

## 选定方案

采用方案 B。

## 实施设计

### 一、页面主骨架

保留 `AppLayout` 和当前真实 API 数据流，但收敛 `DeviceManagementView.tsx` 的页面结构，只保留：

- 统计卡片区域
- 设备列表卡片
- 搜索/筛选/操作按钮区
- 批量选择提示条
- 规范模态弹层

移除会把页面拉回旧版形态的残留逻辑或冗余调用点。

### 二、批量操作体系

批量更新只保留一套入口与一套展示实现：

- 如果 `BulkOperationModal` 已不在设备页使用，则删除其在设备页主链路中的历史影响。
- `BulkDeviceUpdate` 改造为符合当前模态体系的实现，确保只在弹层中展示。
- `DeviceManagementView` 只和这一套批量更新组件对接。

### 三、测试策略

优先补/改前端测试，刻画这三个回归目标：

- 设备页在批量更新时打开的是规范弹层，而不是页面内嵌旧骨架。
- 设备页仍然保留跨页选择与筛选切换清空选择的逻辑。
- 旧组件残留不再影响设备页主渲染结构。

### 四、验证策略

至少执行：

- 设备页相关 Jest 测试
- `pnpm build`
- `pnpm type-check`

必要时追加与批量交互相关的组件测试。

## 风险与控制

- 风险：清理旧批量组件时误删仍在使用的链路。
  控制：先用测试刻画页面行为，再最小化替换入口。

- 风险：UI 恢复时破坏已打通的 API 调用。
  控制：不改后端接口与前端 API 适配层，只改容器与组件接线。

- 风险：批量更新从“错误内嵌展示”改回弹层后，测试断言过时。
  控制：先更新测试，再按测试驱动实现。
